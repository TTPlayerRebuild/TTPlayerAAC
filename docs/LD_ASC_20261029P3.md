# ER AAC LD 与显式 ASC 频率修复

日期：2026-10-29；最终构建 `2026.10.29p3`。接续 [p2 的 Profile 边界](STREAM_PROFILE_BOUNDARIES_20261029P2.md)，本轮修正 FAAD2 2.11.4 的具体语法和频带表问题。没有取消 `AacCore::decode` 的 `consumed <= packet` 检查，也没有为了匹配某个解码器而修改浮点舍入方式。

所有补丁在 `cmake/faad2_compat.cmake`，由 `cmake/faad2.cmake` 对构建目录中的副本应用。下载版本、归档 SHA-256、共享缓存与原 AddIn 不变；修改说明补入 `third_party/faad2/ORIGIN.txt`。原版权头保留，公开 FAAD ABI、插件 ABI 和运行时依赖不变。

## 一、LD 包消费越界：把 ER 尾部当作普通 fill_element

p2 的真实样本 `er_ad6000np_44_ep0.mp4` 是 44.1 kHz、6 声道、512 samples/frame 的 ER AAC LD。旧重建版在第 35 个包（552 字节）遇到 FAAD 报告消费 553 字节，正确触发包边界保护，不能继续播放。

进一步对 FAAD 进行仅在私有构建启用的位位置跟踪，发现错误发生在最后一个 LFE 后：`single_lfe_channel_element` 仍偷看后续三位是否等于普通 AAC 的 `ID_FIL`，随后调用 SBR／fill 解析。这个样本第 35 包在 bit 4409、总长 4416 bits 处触发该路径；剩余位本不应按普通 AAC 的元素 ID 消费。其它越界包也出现同一路径。

FAAD 自己的 `raw_data_block` 已把两种顶层语法分开：普通语法按元素 ID 循环，ER 语法按 channel configuration 决定固定的 SCE／CPE／LFE 序列。两处子元素 SBR 偷看没有同步遵守这一分支。独立的 FFmpeg `aac_decode_er_frame` 同样直接遍历既定声道元素，没有在这些子元素后读取普通 `ID_FIL`。

修复仅将 SCE／LFE 和 CPE 后的两处 `ID_FIL` 偷看限制为 `object_type < ER_OBJECT_START`。没有钳制 `bytesconsumed`，没有扩充逻辑包长度，没有修改容器提供的包数据。仅应用该修复时，302 个包全部通过，PCM 与原来绕过宿主保护、直接调用 FAAD 得到的 PCM 逐字节相同，说明它修复的是错误的尾部消费。

来源：[FAAD2 2.11.4 syntax.c](https://github.com/knik0/faad2/blob/2.11.4/libfaad/syntax.c)。原版 DLL 的 ER LD 仍能输出完整 PCM；重建版保留更严格的包完整性保护，通过修复底层语法让有效文件通过，而不是复刻旧版的越界消费计数。

## 二、LD PCM 偏差：错误沿用 LC／Main 的 TNS 频带上限

修复尾部消费后，旧 FAAD 与原版相近的数值差仍然存在。继续检查发现，`max_tns_sfb` 只区分普通长／短窗和 SSR，LD 仍使用 LC／Main 长窗表。例如 44.1 kHz 被限制到 42 个频带，而 LD 应为 32。

本轮采用三类相互独立的证据：

1. **标准条文**：ISO/IEC 14496-3:2009 §4.6.17.2.5，表 4.172／4.173，分别定义 LD 480／512 样本帧的 TNS 上限；22.05／24 kHz 在两种帧长下的值不同。条文见 [该版标准的公开镜像，第 694 页](https://csclub.uwaterloo.ca/~ehashman/ISO14496-3-2009.pdf#page=695)。
2. **FATE 金样**：FFmpeg 的 `tests/fate/aac.mak` 将该 MP4 的比较目标指定为 [`er_ad6000np_44.s16`](https://fate-suite.ffmpeg.org/aac/er_ad6000np_44.s16)。这里只称它为 FATE 仓库提供的回归参考；没有进一步确认其最初生成工具，不能把文件本身称作 MPEG 标准权威真值。不能误用同目录的 `_ep0.s16` 替代实际 FATE 指定文件。
3. **独立解码**：FFmpeg 9.0.1 的 PCM；同时核查了本地 FFmpeg 9.0.2 的 LD TNS 表及调用路径。

修复将帧长传入私有 `max_tns_sfb`，LD 使用对应的 480／512 表。TNS 解码和 LTP 重建中使用的 TNS 编码路径均得到同样的上限。其他对象类型继续使用原表。

完整样本共 154,624 帧；统一为 Windows 声道顺序后：

| 对照 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 对 FATE `.s16`：最大误差，16-bit LSB | 3537 | **1** |
| 对 FATE `.s16`：RMS，16-bit LSB | 35.7973419 | **0.6139914** |
| 对 FFmpeg 浮点输出：最大绝对误差 | 0.1079350 | **6.5565109e-7** |
| 对 FFmpeg 浮点输出：RMS | 0.0010923 | **4.9122933e-8** |

16-bit 比较将浮点乘 32768、四舍五入并限制到 signed 16-bit；这里只用它评估参考差异，没有改变插件的浮点输出。FFmpeg 对同一 FATE 金样也有最多 1 LSB 的差别，本轮不追逐这类小差异。

这项修复有意改变原 DLL／旧 FAAD 的 LD 输出，是按照 LD 的频带规则修正旧实现，不能同时声称与原版逐位一致。

证据哈希：

- `er_ad6000np_44_ep0.mp4`：`dcc229f067ed9c8c63617d4024f18d6259b8aeabf9ebcfd7a55e8c1f27da2f50`。
- FATE `er_ad6000np_44.s16`：`55d3a3966342fd82347d438e378475d37685b4c7a323ff827b408752fc5197f0`，1,855,488 字节。

## 三、ASC：保留显式频率，并区分 core 与 SBR 输出

FAAD 原先遇到 core frequency index 15 时读出后丢弃 24-bit 频率，接着查索引 15 得到 0，导致 `Init2` 返回 `-2`。仅让容器接纳这个字段不能解决解码器初始化。

现在在解码核心中验证并保留该值：

- 普通 AAC core：只有精确等于现有 FAAD 频率表值时才规范化为相应索引。现有表为 8–96 kHz 的 12 项标准频率；不把 50 kHz 等值四舍五入到临近表项。7350 Hz 仍是既有限制。
- 显式 SBR 和同步扩展：同样处理 24-bit 频率，并在规范化后比较 core／输出频率，正确识别 downsampled SBR。
- SBR 输出还允许精确等于现有 core 频率的两倍，例如 64／88.2／96 kHz core 对应 128／176.4／192 kHz 输出。此时输出保持索引 15，由 FAAD 的既有 SBR 初始化从一半的频率建立 core 表。
- 显式字段不足 24 bits、同步扩展缺失 `sbr_present_flag` 或频率索引时返回错误，不能以位读取器补出的零构成一个“有效配置”。

曾在实现中把 SBR 输出也一律限制到普通 12 项表，这会误拒绝 p2 已经能够处理的 192 kHz 输出，已经纠正。最终用真实编码的 64／88.2／96 kHz AAC-LC 包构造 SBR 上采样配置，覆盖显式 AOT 和同步扩展、索引／显式 core 的四种组合；输出全部与 p2 的相同配置逐字节一致。这是上采样路径回归，不声称这些构造包含高频 SBR 编码数据。

没有扩展 AOT 31 后的音频编码类型，没有支持任意采样率，也没有增加新的重采样器。有效的索引式 Main／LTP／LC／HE／HEv2／多声道回归输出保持不变。

## 五、与 p2 预期的变化及剩余范围

- p2 的 `explicit-rate-with-hint`／`explicit-rate-without-hint` 现在应成功解码，不能继续使用旧的拒绝预期。AOT31 仍不支持，其容器拒绝 HRESULT 以本轮主任务的明确返回值为准。
- p2 中仅绕过消费保护得到的旧 LD PCM 不再是正确性参考：TNS 修正会改变它。完整 LC／Main／LTP／HE 时间轴和保存回归仍应保持原有结果。
- Main channel coupling 仍未恢复。上游 `COUPLING_DEC` 分支本身标注只跳过部分语法，直接开启宏不能等价于完成耦合通道音频重建。
- SSR 未开启，也没有完成其真实样本与综合／增益控制链路验收。
- LD480 的有声内容、其它采样率与 LD LTP 等组合尚未完整实测；本轮不据一个真实 6 声道样本宣称全部 LD 已完成。
- 任意显式频率、7350 Hz 和扩展 AOT 保持明确边界；本轮没有承诺完整 ASC／所有 MPEG-4 Audio 编码支持。
