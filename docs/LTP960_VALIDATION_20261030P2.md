# LTP960 真实编码与完整接口验证（2026-10-30 p2）

此前的“LTP960 已恢复算法及初始化，但缺少真实有声样本”现已推进为：**由真实 PCM 编码得到的八组 LTP960，已确认实际使用长期预测，并通过独立解码器的完整 PCM 对照和公开 AddIn 接口测试。** 本轮没有修改生产解码逻辑，没有增加生产依赖，也没有把已有 1024 帧码流改标志后冒充 960 帧。

这批样本来自明确记录的**私有 FAAC 1.28 验证编码器改造**，并非未经修改的官方编码器，也不是 ISO 发布的历史一致性测试样本。两者的来源差别必须保留。

生产插件维持前轮冻结版本，SHA256：

```text
797175aedd2f538f4a6b5cc03e6e27038128fe064c67b2a462f7275f1b381369
```

## 1. 公开样本与编码器调查

检查了 [ISO/IEC 14496-26 第二版公开语料目录](https://standards.iso.org/iso-iec/14496/-26/ed-2/en/) 的完整文件名清单。普通 LTP 公开条目为 `ap01…ap05_48`，没有找到名称带 `sf` 的 960 帧 LTP 条目。又按 ZIP Range 提取并核对清单 MD5，检查了 `er_ap10_44_ep0`、`er_ap14_44_ep0`、`er_ap27_44_ep0` 三类 ER-LTP 代表文件。ASC 分别为 `9a0900`、`9a09c0`、`9a1160`，均为 AOT 19、`frameLengthFlag=0`，属于 1024 帧。

这证明所检查的条目不满足本次 960 条件；不把有限检索写成“全世界没有官方 LTP960”。旧 MPEG-4 参考编码器来源还存在失效 FTP 或需要另行接受许可的下载入口，本轮没有绕过许可获取文件。

现代 FFmpeg 的 AAC 编码器已不能提供实际 LTP 编码，旧 FFmpeg 的 LTP 选项在本地测试中也有 AOT 4 但实际预测为零的情况，详见 [前轮 LTP/DRC 记录](LTP_DRC_VALIDATION_20261030P1.md)。本轮使用仍含完整 LTP 搜索及量化路径的 [FAAC 官方历史标签 `faac1_28`](https://github.com/knik0/faac/tree/faac1_28)，下载压缩包固定 SHA256：

```text
13c461d2f30be9f7c4423bb62b3c8ea8f750a66f32c68d35a69b7cd06c5894da
```

## 2. 私有编码器究竟修改了什么

FAAC 1.28 已经在 DRM 数学分支中提供 960/120 帧几何、960 频带表及混合基数 KISS FFT。私有宏 `FAAC_LTP960` 只选用这些数学部分，仍通过普通 MPEG-4 AOT 4 写包，没有启用 DRM 的传输或错误保护语法。

具体改动如下，完整补丁保留于私有测试目录的 `faac960.patch`：

| 部分 | 960 路径 |
|---|---|
| 长／短窗 | 实际 960／120 个谱系数；分析和合成使用对应帧长 |
| FFT／频带 | 原有混合基数 KISS FFT 和 960 scale-factor-band 表 |
| 长短窗过渡 | `(960-120)/2 = 420`，不保留 1024 路径的 448 |
| LTP 历史及搜索 | 原动态几何逻辑，最大 lag 为 `2×960=1920`，按实际帧长更新历史 |
| 前向 MDCT 标度 | `N/2=480`，不继续使用 512 |
| ASC | 编码器按真正帧几何写入 `frameLengthFlag=1` |
| 诊断 | 仅在私有编码器记录实际预测搜索与选中状态 |

`faacEncEncode` 的输入是完整 16 位 PCM。路径依次经过实际窗函数、MDCT、LTP 搜索、预测残差、量化和码流写入；生成之后不改 AOT、帧长或谱数据。另用同一源码但不定义 `FAAC_LTP960` 构建 1024 控制编码器，检查控制组没有因几何改造而失真。

私有补丁 SHA256：

```text
74ca5aeb17ba74484b5bce9c663bf1f89e27a96cbb77ef9563ec44fd9d941f51
```

四份输入均为四秒确定性谐波、包络变化和短静音片段，自动切窗与强制长窗使用相同输入。输入 PCM 的 SHA256 为：

| 输入 PCM | SHA256 |
|---|---|
| 44100 Hz／单声道 | `e41315d613cae58df751933abb70f7319ef8c155c2bc72834c37c4e0f2fe49be` |
| 44100 Hz／双声道 | `d72f34b2c672be54737345fe723a253384912f92169ce9d5d363331a3089dcdf` |
| 48000 Hz／单声道 | `c7d297af5a8133b37f7f9422a728e6b260cdb6f695f231ead7d002627c1e55ac` |
| 48000 Hz／双声道 | `d0d206b9f27bbca5557f553a3b8335f4df63edbb4015e127a93981163e187241` |

每声道目标 64 kbit/s，MPEG-4 LTP、允许 MS、关闭 TNS。关闭 TNS 是编码器公开配置；不以错误 TNS 包验证正常播放。自动切窗覆盖长窗、长转短、短窗和短转长；另有强制长窗组用于排除过渡干扰。

初版私有编码器的过渡窗仍沿用 448，AddressSanitizer 报出堆越界。修正为 420 后，四个自动切窗组合再次编码，均退出 0 且无 ASAN 报告。该缺陷属于本轮测试编码器适配过程，**不是生产插件崩溃**。ASAN 与优化 Release 构建的浮点优化不同，不要求二者编码包逐位相同；最终独立对照使用冻结的 Release 包。ASAN 检测只覆盖这四个编码过程，不冒称已经对生产插件做了全覆盖 ASAN 检查。

## 3. 独立参考与实际预测的证据

直接把 FFmpeg 当作 LTP960 真值不可行：检查的 FFmpeg n8.0 与 master `windowing_and_mdct_ltp`、`apply_ltp`、`update_ltp` 仍固定使用 1024／2048；选择了 960 最终 IMDCT 并不等于前向预测也支持 960。对应源码快照及散列保存在私有参考证据中。

独立参考采用 [OxideAV AAC 固定提交](https://github.com/Sec-ant/oxideav-aac/tree/5e71c7556f4b7691bbf8aa7306331e8fb5976ef1)，通过自身解析器、频谱重建、动态 960 几何的 LTP 及 f64 滤波器输出，不调用 FAAD 重建 PCM。

未把未经校准的参考实现直接作为标准答案。其原实现对 LongStart／LongStop 的 LTP 分析错误地始终选择 OnlyLong 窗，导致 1024 控制样本明显偏离 FFmpeg。私有参考副本改用已有的相应过渡窗生成器，保留完整 `reference-calibration.patch`。该补丁 SHA256：

```text
0cd67573e4a7f182a136dd09bb8bc69007b18ed766e6f9a25894ed09cb0bded5
```

修正后的参考先对八个真实 1024 控制流与 FFmpeg 9.0.1 完整 PCM 校准，最大 RMS 为 `1.87633e-7`，最大点误差为 `7.41859e-7`（约 0.00615／0.02431 LSB16）。这八组包括两个采样率、单／双声道、自动／强制长窗。

随后对八个真正 960 流做完整 PCM 对照。公开 Decoder 会隐藏最初一个 overlap 预热帧；独立参考明确仅跳过一个 960 帧，对其余每个输出采样进行比较。1024 控制相应跳过一个 1024 帧。未拟合增益、未搜索有利时间偏移、未逐帧对齐或省略误差较大的帧。

下表的预测次数来自实际解码路径，不只是 AOT 或 predictor 标志的存在。误差采用归一化浮点差乘 32768 的 LSB16 单位。

| 960 样本 | 实际预测调用 | 每声道输出帧 | RMS（LSB16） | 最大误差（LSB16） |
|---|---:|---:|---:|---:|
| 44.1 kHz／单声道／自动 | 173 | 176640 | 0.308402 | 1.677143 |
| 44.1 kHz／单声道／长窗 | 174 | 176640 | 0.311529 | 2.106914 |
| 44.1 kHz／双声道／自动 | 12 | 176640 | 0.012089 | 0.401547 |
| 44.1 kHz／双声道／长窗 | 348 | 176640 | 0.309621 | 2.161992 |
| 48 kHz／单声道／自动 | 189 | 192000 | 0.592469 | 4.737103 |
| 48 kHz／单声道／长窗 | 190 | 192000 | 0.640271 | 4.418581 |
| 48 kHz／双声道／自动 | 196 | 192000 | 0.137619 | 1.441745 |
| 48 kHz／双声道／长窗 | 380 | 192000 | 0.603221 | 4.318369 |

FAAD 使用量化的 `int16_t` LTP 重建历史，独立参考和 FFmpeg 使用浮点历史。该差异与测得的误差规模相符，但未把每一位误差都无条件归因于这一点；因此保留具体误差，不宣称独立输出逐位相同。

进一步在独立参考中只禁用 LTP 贡献，八组的归一化 PCM RMS 差达到 `0.01135～0.13505`。这些明确标为消融实验的输出不能当作正确参考，却能证明所有八组的预测确实参与了声音重建。1024 控制中的 44.1 kHz 双声道自动组预测次数为零，仍保留作控制，不把它算作真实预测正向证据。

## 4. 公开接口、MP4、定位及边界

所有测试通过导出的 `ttpGetSoundAddIn` 使用原 ABI 工厂，既检查独立压缩数据 Decoder，也检查 MP4 Reader→Decoder 和有 edit list 的内部 PCM Reader。

| 项目 | 命令数 | 展开场景数 | 验证内容 |
|---|---:|---:|---|
| 16 组 Decoder 容量与 Reset | 16 | 64 | 65533 字节、3 个采样再多 1 字节、建议一帧大小减 1、单个对齐采样；每组四轮完整 PCM 一致 |
| 16 组普通 MP4 | 16 | 16 | Reader 输出包经 Decoder 后完整 PCM SHA256 一致 |
| 8 组 MP4 edit list | 8 | 56 | 每组全段及 0、1000、500、2500、17、0 ms 六次定位，均与连续 PCM 对应后缀精确一致 |
| 960 lag 边界 | 4 | 4 | 0、1920 可输出有限 PCM；1921、2047 返回错误并清零输出 |
| 合计 | **44** | **140** | 其中包含 **48 次 Reset 整段重放**，不另加到场景总数 |

输出缓冲检查还包括容量小于一个对齐采样时不得消耗待输出帧：返回零长度；存在 PCM 时返回 `ERROR_INSUFFICIENT_BUFFER`，且 `NeedsInput/OutputAvailable` 状态允许扩大缓冲重试。`BufferSizes` 的建议输出容量必须准确等于 `960×nBlockAlign` 或控制组的 `1024×nBlockAlign`。

八个 edit list 容器在相同编码包外加入合法 `elst`，跳过 960 个初始预热采样，将 duration 设置为实际保留 PCM 帧数。48 kHz 为 192000 帧／4000 ms，44.1 kHz 为 176640 帧／4005 ms，保留编码器最后一帧的必要填充。17 ms 在 44.1 kHz 对应 749 帧，接口回报取整后的 16 ms；测试按照实际帧位置比较，不强行要求毫秒文本完全相同。

lag 用例是在**另存的边界测试副本**中，仅把第 2 个包实际 LTP lag 从 873 改为 0／1920／1921／2047。0 和 1920 的散列只用于跨平台稳定性检查，不当作编码器独立产生的音质正向证据；1921／2047 均在该包返回 `0x8007000d`（`ERROR_INVALID_DATA`）及零输出，未放宽原有范围检查。八组原始有声向量没有被改动。

没有生成 ADTS960；ADTS 头无法表达该 `frameLengthFlag`，不能通过改 MPEG-4 配置后声称 ADTS 支持 960。

## 5. 本地复现与系统验收

私有主目录：`rebuild/tests/plugins_followup_20261030p2/aac-ltp960/`。独立参考目录：同层 `aac-ltp960-reference/`。全部源码、第三方下载、输入、音频包、PCM、探针及日志留在 `rebuild/tests`，不上传、不进入 Action、不放入发行包。生产仓库本轮只新增本说明。

主要复现入口：

```text
cmake -S <aac-ltp960> -B <aac-ltp960>/build -A x64
cmake --build <aac-ltp960>/build --config Release
python -X utf8 <aac-ltp960>/generate.py
python -X utf8 <aac-ltp960>/generate.py long
python -X utf8 <aac-ltp960>/make_edits.py
python -X utf8 <aac-ltp960>/public_run.py
python -X utf8 <aac-ltp960>/lag_boundaries.py
python -X utf8 <aac-ltp960>/stage.py
```

前两次 `generate.py` 会重建私有样本，验收时应使用已冻结的向量及散列，不重复生成替换 golden。独立参考的 `run.py`、`calibrate.py` 另负责全段对照和 1024 校准。

最终 VM stage 为 `aac-ltp960/vmstage/`，约 2.86 MiB，只有固定 DLL、4 个兼容 XP 的探针、所需压缩包／MP4、`run.cmd` 和 SHA256 清单，不携带参考 PCM 或编码器。运行结束标记为：

```text
LTP960_COMMANDS=44 LTP960_SCENARIOS=140 RESET_REPLAYS=48 PASS
```

Windows 11、XP、Win7 已使用同一冻结 DLL 和同一 stage 实际执行，三系统均通过全部 44 条命令／140 个展开场景／48 次 Reset 重放；日志分别为 `stage-local.log`、`xp-result.log`、`win7-result.log`。两个旧系统的非法 lag 同样返回 `0x8007000d` 及零输出。原版 5.7.9／重建版实际播放器的宿主验收由主任务另行记录，不能以接口探针代替。

原始来源、输入 PCM、冻结压缩包、MP4 与探针源码散列保留于 `evidence-manifest.json`；实际预测计数在 `generated.json`／`generated-long.json`；独立完整 PCM 比较、FFmpeg 校准和消融数据分别在 `independent-comparison.json`、`calibration-and-prediction.json`。

## 6. 完成范围与仍有限制

本轮补齐的是 **AOT 4、44.1／48 kHz、单／双声道、sine 窗、自动长短窗及强制长窗的真实 LTP960 预测验证**，并且覆盖公开接口、帧长容量、Reset 和准确定位。这些配置未发现需要新增生产修复的缺陷。

仍不把结论扩大到 LTP960 的 TNS、KBD、多声道、ER-LTP、所有 lag／频带组合，或全部合法时钟；此批验证编码器没有产生这些配置。官方历史 LTP960 一致性向量仍未定位，当前的真实 PCM 编码及独立解码证据不能改称 ISO 认证。FFmpeg 现有固定尺寸 LTP 路径的限制也不应回写成重建插件的能力限制。
