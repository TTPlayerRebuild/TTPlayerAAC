# AAC LD480、低采样率与 960 帧补充验证（2026-10-30）

本轮确认并修复了三个实际缺陷：LD 低采样率被误判为隐式 SBR、LD 的部分合法采样率缺少频带/TNS 表映射，以及非二次幂前向 FFT 使 LD480 长期预测产生明显错误。修复集中在 `cmake/faad2_ld_compat.cmake`，构建时只修改 FAAD2 2.11.4 的工作副本；保持原 AddIn 接口和 XP／Win7 构建方式。

同时补充真实有声 LD480/512、LC960 和 7350 Hz Main 的证据。未用更改 `frameLengthFlag` 的方式把 512/1024 帧冒充 480/960 帧。

## 1. 来源及方法

- [ISO 官方 MPEG-4 Audio 符合性语料](https://standards.iso.org/iso-iec/14496/-26/ed-2/en/)：`compressedMp4.zip` 和 `referencesWav.zip`，本地按 HTTP Range 读取选定 ZIP 成员，并与该目录的 `files.md5` 核对。只保留私有测试副本，不提交标准音频。
- [FDK AAC 2.0.3 源码](https://github.com/mstorsjo/fdk-aac/tree/v2.0.3)：本地构建独立编码器及解码器，使用其公开 API；源码未修改。固定源码 ZIP SHA256 为 `8b73e924bd9f12ea0dd1d809e5acd6805e82dc184bc55e99f7964f6850e378ef`。
- ISO/IEC 14496-3:2009：表 4.82、4.172/4.173，以及 §4.6.7、§4.6.17，用于频率表映射、LD TNS 和 LTP 几何关系核对。
- FFT/MDCT 另用直接 DFT/余弦定义作独立数值比对；不依赖某个解码器作为唯一结论依据。
- 全部脚本、下载、参考 PCM、数值探针和运行日志在 `rebuild/tests/plugins_followup_20261030/aac-ld/`，不进入 Action，也不打入发行包。

## 2. 已修复的问题

### 2.1 低频 LD 被普通 AAC 的隐式 SBR 推断误伤

真实 FDK LD16/22.05/24 kHz 输入初始化时分别被报成 32/44.1/48 kHz；首包随后返回数据错误。原因是 ASC 中没有显式 SBR 标志时，普通 AAC 的低采样率猜测也应用到了 LD。

修正排除了 LD 的隐式 SBR 猜测。只改变该对象类型，不改变既有普通 AAC-LC 的低频默认行为。输出格式和解码帧均使用真实核心时钟。

### 2.2 LD 频带与 TNS 表未覆盖合法的高、低频率

FAAD 原表只填充 LD 22.05/24、32、44.1/48 kHz 对应项。8/11.025/12/16 和 64/88.2/96 kHz 的真实 FDK LD 流因此缺表。

依据频率相关表缺失时选择最近已定义表的规则，在 LD 的局部表索引上采用：低频使用 22.05/24 kHz 族，高频使用 48 kHz 族。未修改真正的 PCM 时钟。480 帧低频 TNS 上限为 30，512 帧为 31；44.1/48/32 kHz 的原上限保持不变。

7350 Hz 使用与有效 8 kHz LD 相同的频带族。此前特殊拒绝 7350 LD 的保护已由合法同表族有声证据替代；跨频带族直接修改 ASC 的旧负例不具有正向格式有效性，不能据此认定合法 7350 LD 不支持。

### 2.3 LD480 的长期预测前向 FFT 错误

ISO `er_ad1103_22_ep0` 和 `er_ad1103_32_ep0` 都能完整解析，但旧实现相对官方 PCM 的最大浮点误差分别约 0.227 和 0.579；对应无预测 `np` 样本正常。

根因是 `cfft.c/passf5` 的前向 radix-5 蝶形在合成 `c4/c5` 时交换了系数。方向符号已由后续输出运算处理，两个方向应使用相同的中间组合：

```text
t5 = x1 - x4
 t4 = x2 - x3
c5 = sin(72°) * t5 + sin(36°) * t4
c4 = sin(36°) * t5 - sin(72°) * t4
```

修复两处分支，逆向 FFT 不变。LD480 的 960 点前向 MDCT、普通 LTP960 的 1920 点前向 MDCT 共用该路径。后者的数学变换已验证，但尚无真实 LTP960 码流验收，不能把数学单元验证写成该格式端到端已验证。

直接计算的 960 点 MDCT 最大误差从约 106.9 降至约 0.00003；1920 点从约 46.0 降至约 0.0002。1024/2048 点原有结果不变。探针按理论缩放系数 2 检查，未通过拟合缩放掩盖错误。

### 3.3 7350 Hz LD 与 Main

FDK 2.0.3 编码器不接受原生 7350 Hz。使用真实 8 kHz LD 编码结果，在相同频带族内仅改变 ASC 时钟；不改变任何音频包、帧长或频谱数据：

- LD480/512 × 单/双/六声道 × indexed/explicit ASC，共 **12 组**。
- 输出实际为 7350 Hz，完整 PCM 与原 8 kHz 解码逐位相同，时长按真实时钟计算。
- 这些应称为“合法同频带族时钟变换向量”，不称为“FDK 原生编码 7350”。

Main 使用 ISO `am00_08` 有声规范包，除 ASC 和其中 PCE 的频率字段外保持数据不变。7350 indexed/explicit 两组输出均为单声道、7350 Hz、523264 帧；按普通 AAC 首帧 1024 预热对齐后，对官方 8 kHz WAV 最大浮点误差 `2.384e-7`、RMS `4.753e-8`。因此 7350 Main 已有有声证据。

### 3.4 真实 LC960

ISO `al00sf_44.mp4` 的真实 ASC 设置 960 帧长，323 个包；官方参考共 310080 帧。FAAD 普通 AAC 路径跳过初始 960 预热帧，输出 309120 帧：

- 对齐官方 WAV：max `1.341e-7`、RMS `3.668e-8`。
- 对齐独立 FFmpeg 解码：max `9.686e-8`、RMS `1.403e-8`。

FDK 2.0.3 解码器可处理相关几何，但其公开编码器 `AACENC_GRANULE_LENGTH` 不接受 960（返回 `AACENC_INVALID_CONFIG`）；未用它伪造 LC960。

补充低频 LC960：ISO `al06sf_08.mp4` 是真实 8 kHz、960 帧、三声道数据。音频包全部保留，只将同表族 ASC/PCE 的时钟改为 7350 Hz，indexed/explicit 两组均输出 61440 帧；与独立 FFmpeg 对原 8 kHz 样本的完整输出按首个 960 预热帧对齐后，最大浮点误差 `1.788e-7`、RMS `1.677e-8`。此证据补齐了 7350 LC960 的有声覆盖。

### 3.5 不能把 FFmpeg 的 LD480 输出作为唯一真值

本机 FFmpeg 9.0.1 的 LD480 输出与 FDK/ISO/已修正 FAAD 有明显差异。已核对本地 FFmpeg 9.0.2 源码 `aacdec_dsp_template.c/imdct_and_windowing_ld`：该分支仍固定使用 512 点 MDCT 和 256/192/128 等重叠长度。相邻 ELD 分支有帧长选择，LD 分支没有。

因此本轮 LD480 使用真实 FDK 编解码和 ISO 官方 WAV 验证；512 帧仍可用 FFmpeg 交叉比较。这是参考工具的限制，不用其错误输出驱动兼容补丁。

本机验收 DLL：`ttp_aac/build/Release/ttp_aac.dll`。各阶段具体 SHA256 见私有 `vmstage/manifest.json` 及父任务总验收报告；统一审查后的最终 DLL 为 417792 字节，SHA256 `68c95cb8b51fd0efcb75510cb33dcdcead455918334058bd96b6e28981f6f4bf`。本机仅替换 DLL 后重跑 101 项通过，PCM golden 未修改。

私有平铺目录 `rebuild/tests/plugins_followup_20261030/aac-ld/vmstage/` 约 **9.86 MiB**，含 `run.cmd`、兼容 XP 的 `ld_probe.exe`、包数据、清单与 SHA256。未复制完整参考 PCM 到虚拟机。

本机运行 `run.cmd`：**LD_CASES=99 FAILURES=0**；追加 `run-lc960.cmd`：**LC9607350_CASES=2 FAILURES=0**，总计 **101 个音频用例**。最终 DLL 替换后原有 99 项 golden 未改变。构成为 72 组 FDK LD、12 组 LD7350、12 组官方 LD、1 组真实 LC960、2 组 Main7350。每组验证实际频率、声道、完整总帧数、无 NaN/Inf，以及完整 PCM SHA256。`stage.py` 支持用指定最终 DLL 建立/运行 stage；刷新 golden 前必须独立核对输出变化原因。

## 5. 原版对照与仍未完成的证据

- 对原版 `D:/Programs/TTPlayer/5790/AddIn/ttp_aac.dll` 的只读 ABI 探针有单独 `original-comparison.json`：LC960 能给出数据；7350 Main 初始化返回 `E_FAIL`；部分 LD 接口调用输出不完整，低频 LD480 直接调用还出现访问异常。这只是该探针路径的观测，不能代替原版 UI 宿主验证，更不能把重建版的新正确性修复宣称为与旧 DLL 逐位一致。
- **LTP960、7350 LTP** 仍缺可靠真实有声码流。现有 LTP960 前向 MDCT 的数学验证已通过，合法 LTP960 初始化也已由 SSR guard 修正恢复（上游把 AOT 4 错当 SSR AOT 3）；尚不能据此宣布端到端验收完成，也不能反过来认定功能未实现。
- **7350 核心的 SBR** 仍是本实现明确拒绝的边界。本轮没有获得可验证的真实 SBR7350 样本或完成对应 SBR 表族验证；没有把“当前拒绝”改写为“该组合在全部规范中非法”。
- FDK 不编码 LTP，当前 FFmpeg AAC 编码器也拒绝 `aac_ltp` 配置；这些是测试编码器能力限制，不是重建 DLL 的失败证据。
- SSR 的 960 帧属于另一问题：ISO 的 SSR `frameLengthFlag` 要求为 0；不应借本轮 LD/LC960 修改扩出 SSR960。
- 所有用户文件、原始 DLL 和原 EXE 均未修改；官方语料和测试源码只存在私有 tests 目录。
