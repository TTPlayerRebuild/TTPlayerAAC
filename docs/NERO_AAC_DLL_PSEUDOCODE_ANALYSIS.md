# Aac.dll 伪代码与二进制分析

`AddIn/Aac.dll` 实现了 Nero 音频插件接口、AAC 读取与解码、编码任务管理、MP4 容器与标签处理，以及 MFC 配置窗口。生成 AAC 压缩帧的编码核心由外部 `aacenc32.dll` 提供。因此，恢复 `Aac.dll` 的宿主接口和界面具有明确路径，但仅分析这个 DLL，还不足以独立重现 Nero 编码算法。

本文分析日期为 2026-10-06，面向当前 TTPlayer 工作区中的二进制。函数地址使用首选映像基址 `0x10000000`；实际加载地址改变时，应使用 `实际模块基址 + RVA`，不能直接使用本文 VA。

配套的 `aacenc32.dll` 为 1,150,976 字节，文件版本 `3.2.0.30`；`NeroIPP.dll` 为 1,564,672 字节，文件版本同为 `3.2.0.30`。这些版本字段属于各自组件，不能用编码核心的版本号替代 `Aac.dll` 版本。

本地分析材料位于工作区 `rebuild/tests/nero_dialog/`：

- `native_analysis/nero/decompiled/Aac.dll.pseudo.c`：初始全模块反编译。
- `native_analysis/nero/decompiled/Aac.dll.functions.csv`：初始函数导出状态。
- `Aac.focused.pseudo.c`：补识别虚函数入口、修正关键调用参数及栈探测函数后的重点反编译。
- `aac-disassembly.txt`、`aac-imports.txt`：二进制交叉核对材料。

初始导出记录包含 3,910 个函数，其中 3,908 个反编译成功，`100D30F9`、`100D3102` 失败。这里的“成功”仅表示生成了伪代码。它不代表参数类型、类成员、调用约定均已正确恢复，也不代表全部函数都经过逐项人工核对。

例如，最初遗漏了通过虚函数表调用的编码写入和配置入口；收尾函数中的栈变量又受到 `_alloca_probe` 识别错误影响。本次补识别了相应入口，并对外部编码调用参数、虚表与关键分支进行了交叉核对。仍不把伪代码中的 `extraout_ECX`、未初始化局部变量或空 `this` 表达式直接认定为原程序缺陷。

## 模块职责与 TTPlayer 的调用范围

| 层次 | 实现位置 | 主要职责 |
| --- | --- | --- |
| TTPlayer 插件接口 | 原版及重建版 `ttp_aac.dll` | 向播放器提供 Reader、Encoder、标签等接口 |
| Nero 插件接口 | `Aac.dll` | 对象枚举、工厂、配置、读写对象、引用计数 |
| Nero 编码管理 | `Aac.dll` | 参数整理、PCM 缓冲、声道重排、首尾处理、容器写入 |
| AAC 编码核心 | `aacenc32.dll` | 通过导出的流式接口生成 AAC 压缩帧 |
| 配套计算组件 | `NeroIPP.dll` | Nero 配套运行组件；内部算法范围需要单独分析 |
| AAC 读取与解码 | `Aac.dll` 内部代码 | 裸 AAC、MP4 音轨读取、解码、定位 |
| MP4 容器与标签 | `Aac.dll` 内部代码 | atom、样本表、轨道、标签、重写和导出 |
| 配置和属性界面 | `Aac.dll` 内部 MFC | 主配置窗口、计算器、文件属性及本地化 |

当前 `ttp_aac/src/nero.cpp` 枚举 Nero 对象后，仅选取类型值为 `4` 的编码器。重建版平常播放 AAC 时，使用自己的容器读取和 FAAD2 解码分支，**不会把普通播放转交给 `Aac.dll` 中的 Nero Reader**。

`Aac.dll` 的 RTTI、构造和对话框代码包含 `CDialog`、`CWnd`、`CComboBox`、`CButton`、`CEdit` 等 MFC 类型。它的界面使用静态链接的 MFC；重建播放器接入 WTL，不会改变这个外部 DLL 的界面实现。

内置解码器的状态结构、配置、初始化、帧信息和定位复位流程与 FAAD 系列接口形态相符；MP4 代码包含 `MP4File`、`MP4MakeIsmaCompliant` 等标识。可以据此识别实现家族和职责，不能据此确定精确上游版本、全部修改或授权范围。有关原 `ttp_aac.dll` 的 FAAD2 结论，也不能直接移用到另一个文件 `Aac.dll`。

## 导出接口与对象模型

### 两个导出函数

| 地址 | 导出 | 实际作用 |
| --- | --- | --- |
| `10011A30` | `NERO_PLUGIN_GetPrimaryAudioObject` | 返回主对象并增加引用；空输出指针返回失败 |
| `10011A08` | `NERO_PLUGIN_ReadyToFinish` | 检查主对象和两个工厂的引用数，判断模块是否可以结束使用 |

`ReadyToFinish` 是模块生命周期检查。每首歌曲的编码结束由编码对象的控制接口完成，不能用这个导出代替。

`10003340` 初始化静态对象；`1001186C` 处理主对象的 `QueryInterface`。枚举数量方法 `10077E60` 的机器码直接返回 `2`，`100119A0` 分别返回：

| 枚举索引 | 描述接口 | 类型值 |
| --- | --- | --- |
| 0 | Reader 工厂的描述接口 | `3` |
| 1 | Encoder 工厂的描述接口 | `4` |

越界枚举会清空输出并失败。正常取得对象后均需要匹配释放。

### 混合调用约定

Nero 接口混合使用 `stdcall` 的 `IUnknown` 方法与 `thiscall` 的扩展方法。同一个对象包含多个接口子对象；其接口指针并不都指向对象起点。工厂的 `IUnknown` 子对象位于当前工厂指针的 `+4`，已有适配器专门处理了这一点。

下表名称是重建适配器使用的语义名称，不是假定恢复出的原始 C++ 类名。

| 接口 | GUID |
| --- | --- |
| 枚举 | `FC2E77B1-6278-452B-9756-7AC24E807778` |
| 编码工厂 | `BB980E93-637F-4373-8F7D-A8AA103CA732` |
| 配置 | `F50907A0-C032-4935-A3E0-832003E44F06` |
| 输出路径 | `FA6A3CF1-E837-42C2-ADDC-8B5044D6848E` |
| 写入 | `B011FB4D-3A88-4A32-BCD6-DBF0DDBFCFC0` |
| 编码控制 | `B388F5E3-94B2-40FF-BCE9-0AC8DBF551CB` |
| 标签 | `FB863BAF-AB38-4851-8B61-1402B27D2FA4` |
| 音轨编号 | `B6062833-ECE6-4716-A6EC-F96A085AAC14` |

`1000AF68` 创建大小为 `0x8100` 字节的编码实例，设置各接口虚表，复制工厂中的选项，并保存输入 PCM 的采样率、位深、声道数。单独的编码实例有自己的流和缓冲，但工厂默认配置是共享状态。这不构成整个旧编码组件可以无条件并行调用的证明。

## 编码调用流程

| 阶段 | 主要函数 | 行为 |
| --- | --- | --- |
| 创建实例 | `1000AF68` | 复制选项、保存 PCM 格式、构造接口 |
| 设置路径 | `10003B60`、`10003C24` | 校验并保存输出路径 |
| 开始 | `10003D3C` | 建立输出文件和轨道、打开核心、预热 |
| 写入 | `10005BA0` | 缓冲 PCM、重排声道、编码和写 MP4 样本 |
| 结束 | `10004A48` | 补尾、排空、写标签、整理容器及可选 AAC 导出 |

路径设置成功只说明前置检查通过。实际文件建立和编码流打开发生在开始阶段，调用方需要分别检查两步结果。

### 开始编码

`10003D3C` 先根据选项调整实际编码参数，包括单声道输出、采样率、Profile 和带宽等。代码中有低于 `24000` Hz 时修改 Profile 的分支，以及按码率和声道数选择参数表的分支。

随后建立或修改 MP4 文件：

1. 已有路径会被打开检查，查询其中的视频轨道。
2. 在无法读取为有效 MP4、或者未找到相应视频轨道的分支，会执行 `DeleteFileA` 后重新建立文件。
3. 对可复用的视频 MP4 存在修改并加入音频轨道的分支。
4. 新建音频轨道使用对象类型 `0x40`；文件 movie timescale 设为 `90000`。

这里是旧组件的实际覆盖行为。因此主程序应在受控输出路径上调用它，不能把“只是配置编码器”和“正式开始编码”混为一谈。

直接导入的核心接口共五个：

| 接口 | 用途 |
| --- | --- |
| `aacStreamOpen32` | 根据编码参数打开编码流 |
| `aacStreamEncodeFrame32` | 编码一批 PCM 样本 |
| `ResetSbrHeaders` | 重置 SBR 头状态 |
| `aacStreamClose32` | 关闭流 |
| `aacStreamDestroy32` | 释放流对象 |

打开调用在机器码层面有 18 个栈参数。并非所有参数的原始类型和名称均已恢复，不能照搬初始反编译器生成的函数声明作为 SDK。

流打开后，插件用清零的 PCM 连续编码两次，再重置 SBR 头。两次预热输出不作为普通歌曲样本直接写入。这说明输入第一帧、核心输出第一帧、MP4 保存第一帧并不是同一个概念。

### PCM 缓冲与声道顺序

`10005BA0` 先把宿主输入复制到内部待处理缓冲，再逐帧编码。Profile 值为 `5` 的分支与其它分支使用不同的帧长：

| 分支 | 每声道输入样本 | 16 bit 下每声道字节数 |
| --- | --- | --- |
| 普通分支 | 1024 | 2048 |
| Profile 5 分支 | 2048 | 4096 |

代码中的处理条件是 `待处理字节数 > 一帧字节数`，并非 `>=`。恰好剩下一帧时，会留到下一次写入或结束阶段处理。这个细节影响短音频和整帧边界，恢复时不能在未对照输出的情况下随意改变。

六声道路径以 16 bit 样本重排：

```text
输入索引  0 1 2 3 4 5
输出索引  2 0 1 4 5 3
```

如果输入采用常见的 `FL FR FC LFE BL BR` 顺序，结果就是 `FC FL FR BL BR LFE`。这里的索引变换由代码确认；声道名称取决于宿主输入约定。重排发生在插件自己的输入副本内。

当前重建适配器接受整数 8/16/24/32 bit 和 float64 PCM，先统一转换为 16 bit 再交给 Nero；采样率限制为不超过 `48000` Hz。适配器的参数检查与旧 DLL 内部真正支持的配置应分别看待，例如“允许传入某个声道数”不等于编码核心一定能处理它。

### 开头延迟与结尾样本

编码写入维护帧计数，跳过最早的输出，并给 MP4 样本设置持续时间和呈现偏移。关键值为：

| 帧计数 | 普通分支偏移 | Profile 5 分支偏移 |
| --- | --- | --- |
| 2 | `0x400`，即 1024 | `0xE00`，即 3584 |
| 3 | 0 | `0x600`，即 1536 |
| 后续 | 0 | 0 |

这些值传给 MP4 样本写入函数 `1005F90C`，不是额外向 PCM 文件写入同样数量的静音。开始阶段的预热和这些偏移共同参与编码延迟处理。

`10004A48` 处理尚未编码的 PCM，补零到完整帧，再追加排空所需的零输入。Profile 5 分支还根据剩余样本数是否大于 `512` 选择处理路径，并调整最后样本的持续时间。最后调用 `Close32` 和 `Destroy32`，恢复保存的输入格式并释放待处理缓冲。

因此，“停止输入后直接关闭编码器”不能复现这份实现。仅验证生成文件能播放，也不足以证明开头、结尾和时长已经一致。

## MP4 封装与附加输出

### 常用容器函数

| 地址 | 作用 |
| --- | --- |
| `1005F2F0` | 打开 MP4 读取 |
| `1005F3F4` | 创建 MP4 |
| `1005F504` | 打开 MP4 修改 |
| `1005F70C` | 关闭 MP4 |
| `1005FBE4` | 新增音频轨道 |
| `1005FF34` | 设置解码器配置 |
| `1005F90C` | 写入压缩样本及时间信息 |
| `10060518` | 读取压缩样本 |
| `1006108C` | 执行 ISMA 兼容处理并关闭 |
| `1005F608` | 优化重写 MP4 |

结束阶段先关闭当前容器，再调用 `1006108C` 和 `1005F608`。前者进入 `1006F3F8`，其中直接包含 `MP4MakeIsmaCompliant` 标识，并处理对象描述、场景描述和 SDP 等旧流媒体兼容内容。后者进入 `10063CCC`，重建输出文件并重新复制轨道数据，未指定新文件名时使用临时文件替换。

这意味着结束阶段有额外文件 I/O，也可能改变 MP4 结构。不能把它等同于一次 `fclose`。虽然配置里保存了 `DefOptimize`，在已确认的编码收尾调用点没有看到用该字段跳过上述调用的条件；不能仅凭选项名断言关闭它就能消除全部收尾重写。

### Hint 轨道与已有视频

启用流媒体 hint 选项时，结束阶段会查询轨道类型和编码类型，并调用对应的打包函数。AAC 路径进入 `100CD224`，可见包大小参数 `0x5DC`，即 1500。

容器辅助代码还包含视频及其它音频类型的分支。这说明其容器库的能力比 TTPlayer 的 AAC 转换界面更广，不能据此认定 TTPlayer 已提供视频编码功能。

### 导出裸 AAC

选择“导出 ISO 13818-7 AAC 流”后，插件在 MP4 收尾之后重新打开容器、读取音频样本，再通过 `100CBAA0` 生成带 ADTS 帧头的 `.aac`，并清理中间输出。

这是重新封装步骤。将 `.mp4` 或 `.m4a` 单纯改名为 `.aac` 无法替代它，MP4 中的标签和呈现时间信息也不能直接当作 ADTS 头的一部分搬过去。

## 标签实现及限制

编码实例通过专用接口接收标签，收尾时写入 `moov.udta.meta.ilst`。主要映射如下：

| 字段 | 包装函数 | MP4 项 |
| --- | --- | --- |
| 标题 | `1006124C` | `©nam` |
| 专辑 | `1006138C` | `©alb` |
| 艺术家 | `100614CC` | `©ART` |
| 编码器说明 | `1006160C` | `©too` |
| 年份 | `100616AC` | `©day` |
| 曲目编号 | `100617EC` | `trkn` |
| 流派 | `10061938` | `gnre` 或 `©gen` |

具体限制来自下层实现：

- `1007285C` 要求年份字符串至少 4 字节，并且只写前 4 字节。完整日期不能按此路径原样保存。
- `100729A0` 查找 148 项标准流派表，匹配时写从 1 开始的编号；未匹配时写自定义文字。
- `100728F0` 可写曲目编号和总数，但编码收尾只传入单字节来源的曲目编号，总数传 `0`。不能据此承诺任意大的曲目编号或完整的 `3/12` 信息。
- 编码收尾对字符串先判断非空。空字符串不等于这里已实现“删除已有标签”的语义。
- 编码器说明读取 `aacenc32.dll` 文件版本，形成 `Nero AAC Codec x.x.x.x`，失败时使用普通名称。
- 字符串写入函数按字节复制，没有在这些 setter 内自动把系统 ANSI 编码转为 UTF-8。当前适配器主动传入 UTF-8，应保留这个边界处理。

本次确认的编码标签接口及收尾调用中，没有完整的封面、AlbumArtist、多值标签写入链路。不能因为 MP4 容器可以容纳这些字段，就认为旧 Nero 编码路径已经实现它们。重建 `ttp_aac` 自身的标签和封面功能是另一条代码路径。

## AAC 读取与定位

### 打开与识别

`1000B8BC` 打开文件，读取大小和时间信息，检查前后附加标签，再进入 MP4 或裸 AAC 分支。可见 `TAG`、`LYRICSBEGIN`、`APETAGEX` 等标识处理，以及 ADTS 同步条件：

```text
byte[0] == 0xFF && (byte[1] & 0xF6) == 0xF0
```

这些检查用于分辨内容和避免把附加标签当作压缩音频，不能理解为只看文件扩展名。裸流分支使用 `0x1200`，即 4608 字节的读入缓冲，并维护帧位置和样本统计。

`1000CC6C` 处理 MP4：枚举轨道，寻找 `soun` 音频轨道，检查 AAC 对象类型，取出解码器配置，再解析采样率、声道和时间信息；还从 MP4 中读取基本标签。它有 SBR 采样率比例处理，容器时间单位和输出 PCM 采样率不能直接混用。

### 内部解码器

| 地址 | 已识别职责 |
| --- | --- |
| `10036910` | 分配并初始化解码器状态 |
| `10036A3C` | 取得配置 |
| `10036A50` | 校验并应用配置 |
| `10036AB8` | 销毁状态 |
| `10037698` | 从音频头初始化 |
| `10037998` | 解析 AudioSpecificConfig |
| `10036BA4` | 帧解码入口，进入 `10036BD0` |
| `10036B88` | 定位后的解码状态调整 |

因此，`Aac.dll` 自带解码实现，并非所有读写都经由 `aacenc32.dll`。后者五个导入接口属于编码操作。

### PCM 读取

`1000EF44` 先消费已解出的剩余 PCM，再读取下一压缩帧。输出容量不足时按样本块对齐返回一部分，剩余部分保留在内部缓冲。

MP4 分支使用样本持续时间与呈现偏移修正输出，包含首帧抑制和需要丢弃的 PCM 数量处理。裸流分支按解码器实际消耗的压缩字节推进，补充输入数据，并避开尾部标签。

代码还区分正常输出、末尾补齐和结束状态。对解码错误、损坏帧及容器时长异常的完整外部表现，仍应通过样本对照验证，不能从某一个 `return 0` 推导所有宿主都会显示相同错误。

### 定位

定位主函数为 `1000FAAC`，分为两种路径：

| 输入 | 定位方式 |
| --- | --- |
| MP4 | 将目标位置映射到轨道时间，查询对应 sample ID 和样本起点，记录帧内要丢弃的 PCM，再调整解码器状态 |
| 裸 AAC | 根据帧位置链表跳到目标附近，或向前解码扫描；复位状态后丢弃目标前的样本 |

它不是简单执行“目标时间乘平均码率，再跳到该文件字节”。裸流路径的索引以逐项分配的链表保存，长文件可在内存分配和索引遍历上产生额外成本；使用连续索引数组有优化空间，但应先保持相同的帧边界和预解码行为。

裸流定位中还存在 `SetFilePointer(..., lowOffset, NULL, ...)` 调用。尽管对象内部部分计数使用 64 位，这一调用点没有传高位，因此不能承诺超大裸 AAC 文件的完整定位能力；具体失败边界需要大文件验证。

## 配置窗口与选项保存

### 界面结构

`1000B20C` 构造并运行 MFC 模态配置窗口，以 `IDOK` 判断成功。当前配置接口的调用只传 `this`，不能额外附加一个自拟的父窗口参数。

主要资源和入口：

| 项目 | 资源或函数 |
| --- | --- |
| 编码配置 | 对话框 `5000`，Nero Digital Audio Coding |
| 码率与容量计算器 | 对话框 `5009`，Bit Rate/Size Calculator |
| 配置初始化 | `100130C4` |
| 翻译和文字尺寸处理 | `10012040`、`10011F54` |
| Reader 文件属性初始化 | `100127A8` |

界面包括预置方案、固定码率、可变码率、目标大小、编码质量、AAC Profile、PNS、hint 轨道、混入已有视频、导出 AAC、单声道及计算器。控件之间有启用状态和参数联动，恢复时需要同时恢复事件逻辑。

对话框资源指定 `MS Sans Serif` 8 pt，运行时另有语言选择、翻译和按文字测量调整尺寸。资源中的初始宽度并不是唯一决定最终窗口尺寸的因素。

### 左侧副屏拉长的原因

`100130C4` 根据复选框文字计算布局时，使用屏幕坐标中的右边界，并把负值与从 `0` 开始的最大值比较。窗口位于主屏左侧时，控件的右边界可以全部为负数，结果却保留为 `0`，随后分组框和窗口被向主屏原点附近拉长。

该问题已在先前任务中用原版和重建版、同为 100% 缩放的左侧副屏复现。宿主现在用限定范围的窗口子类修正尺寸，保留 DLL 自身的配置行为。详见工作区 `rebuild/docs/NERO_CONFIG_MULTIMONITOR_FIX.md`。本次分析没有再次运行那组界面测试。

### 默认值与持久化

`10003700` 的初始配置是 16 个 DWORD：

```text
64, 1, 0, 6, 1, 5, 44100, 15500, 0, 0, 1, 0, 0, 0, 0, 0
```

它包含初始码率、模式、质量、Profile、采样率、带宽和开关值。部分数字是选项枚举值，不能直接作为界面文字显示，也不能认为每次打开都恢复这一组值；工厂和宿主设置会参与覆盖。

`100150DC` 读取、`10006628` 保存以下设置：

```text
DefBitRate          DefVbrMode        DefCodecQuality
DefAacProfile       DefUsePNS         DefHintForStreaming
DefOptimize         DefDownmix       DefMuxIntoVideo
DefExportAAC
```

这些路径通过 `Software\%s\%s\%s\%s` 组合到 HKCU 下，依赖宿主上下文提供的名称。不能直接认定一个固定注册表键适用于所有宿主，也不能因为存在注册表函数就认定当前 TTPlayer 调用路径一定完成了持久化初始化。

另一个独立分支 `10001D74` 查询 HKLM 的 `SOFTWARE\Ahead\Shared` 中的 `Lib`，并调整进程 `PATH`；失败时使用模块所在目录。它用于旧组件路径发现，与上述编码选项保存分开。当前适配器按自身目录加载配套 DLL。

模块还存在试用和授权状态检查。它们参与旧组件的状态与错误提示；替换界面或移除选项注册表读取，不会自动消除编码核心的依赖或授权要求。

## 值得修正与优化的边界

下表区分已确认行为与需要故障注入验证的风险。它不是本次已经完成的代码修复清单。

| 项目 | 静态分析结论 | 后续处理 |
| --- | --- | --- |
| 左侧副屏尺寸 | 已确认坐标错误，已有宿主修复 | 保留限定范围的修复，重写 UI 时统一使用客户区坐标 |
| Unicode 路径 | 旧接口和文件操作使用窄字符串及 `A` API | 保留转换检查；必要时使用可表示的临时路径，成功后用 Unicode API 交付 |
| 输出覆盖 | 开始阶段存在删除已有输出的分支 | 在转换宿主中先准备安全输出，成功后提交 |
| PCM 缓冲复制 | 写入时扩容并复制，处理后又为余量分配和复制 | 用保留容量与读写位置减少重复分配，保持原帧分组规则 |
| 分配失败 | 部分编码缓冲分配后未见就地空指针处理 | 增加失败路径并验证释放行为；暂不宣称已复现崩溃 |
| 错误结果传播 | 帧写入结果被循环后续结果覆盖；部分收尾调用未检查返回值 | 保留首次错误，继续必要清理；用写入失败测试验证 |
| 共享配置 | 工厂配置和宿主上下文为共享状态 | 并发创建与配置需要明确同步，核心线程安全另行验证 |
| 年份与曲目编号 | 年份固定 4 字节；编码轨道编号来源为单字节 | 区分旧接口兼容行为和扩展元数据能力 |
| 长裸流索引 | 链表分配和遍历；部分定位只传文件偏移低位 | 连续索引和完整 64 位文件 I/O |
| MP4 收尾 | 有 ISMA 处理及重写文件步骤 | 保持结构兼容后，再评估一次写完或可选整理 |

性能优化应首先针对缓冲和文件 I/O。仅优化 `Aac.dll` 的这些部分，无法直接改变外部编码核心的声学模型、压缩质量或主要计算算法。

## 重建路径与验证顺序

### 首先恢复接口和宿主行为

保留原核心时，可先恢复两个导出、对象枚举、混合调用约定、创建和释放规则，以及配置窗口的确认与取消行为。将 UI、配置存储和单次编码参数分开，避免配置窗口直接改动正在运行的任务。

随后恢复开始、逐块写入和结束的状态转换。优先对照短音频、恰好整帧、多个输入块及六声道，验证预热、声道重排、初始偏移和尾帧持续时间。

### 再恢复容器与元数据

分别验证普通 MP4、已有视频 MP4、hint 轨道、ISMA 结构及 ADTS 导出。标签需要覆盖标准与自定义流派、非 ASCII 文字、空值、完整日期和较大曲目编号。旧接口不能表达的字段应通过明确的扩展路径补足。

### 最后决定是否替换编码核心

重写 `Aac.dll` 并继续调用原 `aacenc32.dll`，可以保留原核心算法，但仍要对照外围参数和输出结构。想移除全部 Nero 组件，则还需要分析 `aacenc32.dll`、它与 `NeroIPP.dll` 的交互，或者选择另一套编码实现。

更换编码实现可追求功能等价，但不能预先承诺与旧 Nero 压缩比特流、音质取舍、延迟和文件大小完全一致。应分别定义验收目标：

1. 宿主兼容：原版与重建版正常枚举、配置、编码、取消和释放。
2. 音频正确：样本数、时长、定位、声道、头尾无异常。
3. 容器正确：标签、音轨、时间表、导出和重读结果符合约定。
4. 原样程度：在固定旧核心及相同参数下，再比较帧载荷、时间表与最终文件差异。

当前结论属于静态分析；没有新增 XP、Win7、Win10 或 Win11 运行验证，也没有替换生产 DLL。初始反编译成功数量、已有宿主测试和本次函数核对各自覆盖不同范围，不能合并表述为整个 DLL 已完全重建或全平台验证通过。
